# Рекомендуемая стратегия подготовки и чанкинга данных для RAG

Проблема: Слишком мелкие фрагменты теряют контекст, а слишком крупные размывают эмбеддинги и перегружают промпт лишней информацией.

## 1. Основные принципы

- Разбивать текст по смысловой структуре, а не по фиксированному количеству символов. 
- Соблюдать границы заголовков, подразделов, абзацев и предложений.
- Каждый чанк должен быть понятен без чтения соседних чанков.
- Размеры измерять токенизатором выбранной embedding-модели.
- Не разделять связанные списки, таблицы и предложения.

## 2. Рекомендуемые размеры

Для энциклопедических материалов:

- целевой размер чанка — 350–700 токенов;
- допустимый максимум — 800–1000 токенов;
- минимальный полезный размер — 100–150 токенов;
- перекрытие (overlap) — 0–15 %, только при вынужденном разделении одного подраздела.

Для русского текста фиксированного соотношения между символами и токенами нет. Ориентировочно 1 токен занимает 2–4 символа, поэтому 1000 символов — это примерно 250–500 токенов, а 1800 символов — примерно 450–900 токенов. Точное количество следует определять токенизатором выбранной embedding-модели.

Начальная конфигурация для текущего проекта:

- размер — 400–650 токенов;
- overlap — до 50 токенов;
- полный путь заголовков в каждом чанке;
- применение схемы parent-child для больших статей.

## 3. Структура чанка

В текст каждого чанка следует добавлять название документа, тип сущности и путь раздела:

```text
Документ: Вулканцы
Тип сущности: раса
Раздел: Физиология > Мозг

Вулканцы обладали врождёнными телепатическими способностями...
```

Заголовки следует сохранять одновременно:

1. в metadata;
2. в тексте, который передаётся embedding-модели.

Технический разделитель  `#`, `##`, `###`, `####` можно использовать при подготовке файлов, но передавать его в embedding не надо.

## 4. Metadata

Рекомендуемый набор полей:

```json
{
  "franchise": "Star Trek",
  "document_id": "<SHA256 от нормализованного source_file>",
  "title": "Вулканцы",
  "original_title": "Vulcan",
  "entity_type": "race",
  "section_path": ["Физиология", "Мозг"],
  "language": "ru",
  "source_file": "SourceFiles/Races/Вулканцы.txt",
  "chunk_index": 12,
  "updated_at": "2026-10-11"
}
```

Поле `franchise` явно указывает, что материал относится к Star Trek. Поле `source_file` содержит путь к исходному файлу проекта.

`document_id` вычисляется как SHA256 от нормализованного относительного пути к исходному файлу:

```text
document_id = SHA256("sourcefiles/races/вулканцы.txt")
```

Перед вычислением хеша путь необходимо привести к нижнему регистру, заменить `\` на `/` и нормализовать Unicode в форме NFC. Благодаря этому один и тот же путь даст одинаковый идентификатор на Windows и других операционных системах. При переименовании или перемещении файла `document_id` изменится.

## 5. Правила для разных типов материала

### Энциклопедические статьи

- Один смысловой подраздел формирует один или несколько чанков.
- Короткие соседние абзацы одного подраздела можно объединять.
- Длинный подраздел нужно делить только по границам абзацев или предложений.
- Каждый фрагмент должен содержать полный путь заголовков.
- Обозначение «продолжение 2» не должно быть единственным указанием на контекст.

### Карточки объектов

Для кораблей естественной единицей является один корабль. Такой блок желательно индексировать целиком. Если он превышает максимальный размер, его следует разделить на:

- общие характеристики и капитанов;
- историю службы;
- технические особенности.

В каждом дочернем чанке необходимо повторять название и регистрационный номер корабля.

### Списки и таблицы

- Не отделять пункты списка от вводной строки.
- Сохранять пары `поле: значение`.
- Большие таблицы делить по строкам, повторяя названия столбцов.
- Короткие однотипные записи можно объединять по 5–15 элементов.

## 6. Подготовка исходного материала

Перед чанкингом необходимо:

1. Удалить навигацию, рекламу, меню, служебные разделы и повторяющиеся футеры.
2. Сохранить иерархию заголовков `H1 → H2 → H3`.
3. Нормализовать Unicode, пробелы и переносы строк.
4. Не изменять имена, номера кораблей, коды серий и другие точные обозначения.
5. Сохранять связь текста со списками, таблицами и заголовками.
6. Удалять точные и почти точные дубликаты.
7. Хранить путь к исходному файлу, дату загрузки и версию документа.
8. Помечать машинный перевод.
9. Проверять факты и не смешивать без маркировки источники разной надёжности.

## 7. Parent-child chunking

Для больших статей рекомендуется двухуровневая схема:

- child chunk размером 250–500 токенов используется для поиска;
- parent chunk размером 800–2000 токенов передаётся LLM после обнаружения подходящего дочернего фрагмента.

Такая схема повышает точность поиска и одновременно предоставляет модели достаточный контекст.

## 8. Перекрытие

Большое фиксированное перекрытие создаёт дубликаты результатов. Рекомендуется:

- не использовать overlap между законченными подразделами;
- переносить 1–2 предложения при искусственном разделении длинного текста;
- удалять повторяющиеся соседние чанки перед передачей контекста LLM.

## 9. Поиск

Для корпуса Star Trek желательно применять гибридный поиск:

- embeddings — для смысловых вопросов;
- BM25 или полнотекстовый поиск — для имён, кодов и обозначений вроде `NCC-1701-D`;
- metadata-фильтры — для франшизы и типов сущностей;
- reranker — для финальной сортировки найденных фрагментов.

## 10. Оценка качества

Для выбора параметров нужно подготовить 30–100 реальных вопросов и сравнить несколько вариантов:

- 250–400 токенов;
- 400–700 токенов;
- 700–1000 токенов;
- parent-child chunking.

Для каждого варианта следует проверить:

- находится ли правильный фрагмент в top-3 или top-5;
- достаточно ли найденного текста для полного ответа;
- не теряются ли факты на границах чанков;
- не возвращаются ли почти одинаковые чанки;
- умеет ли система отвечать, что информации в базе нет.
