# Рекомендуемая стратегия по разбивке чанков по ТЗ

Стратегия выведена из задания на Corrective RAG MCP-сервер. В тексте нет готовых размеров чанков: прямо сказано подобрать разбивку по природе данных (текст и код) и описать её в отчёте. Размеры и правила ниже следуют из того, как устроены поиск, оценка чанков и маленькая локальная модель.

## Что в тексте задаёт форму чанка

Чанк — единица всего пайплайна, а не только нарезки файла.

1. `index_folder` режет файлы, считает эмбеддинги и кладёт их в ChromaDB, затем заново строит BM25 в памяти.
2. Поиск гибридный: BM25 ловит точные слова и идентификаторы, вектор — смысл, списки сливаются через RRF.
3. Grade Chunks — локальная LLM (Phi-3-mini или Qwen2.5-3B) отвечает по каждому чанку «релевантен / нет». Если релевантных мало, запрос расширяется, и поиск повторяется не больше двух раз.
4. В ответ попадают источники. Критерий приёмки прямо требует метаданные «источник» и «позиция».
5. Проверочные факты — редкие числа, имена и даты, которых нет в открытых источниках. Они должны целиком лежать в базе, иначе модель ответит из своих знаний, и проверка на шаге 5 провалится.
6. Обязательные форматы разные по природе: `.md`/`.txt`, код `.py`/`.js`/`.ts`, структура `.json`/`.yaml`.
7. Эмбеддинги по умолчанию — встроенные в ChromaDB. Внешняя модель (`nomic-embed-text`) — необязательное переключение через конфиг.

Отсюда одно требование: чанк должен быть понятен сам по себе и маленькой модели, и BM25, и эмбеддингу. Слишком мелкий фрагмент не пройдёт оценку релевантности. Слишком крупный размоет вектор, займёт контекст генерации и чаще всего обрежется дефолтной моделью эмбеддингов Chroma (практический потолок около 256 токенов).

## Подготовка данных до индексации

Индексатор сканирует папку по glob и не чистит вики. Грязь нужно убрать заранее.

- Оставить только текст, который можно цитировать: без меню, навигации, рекламы и повторяющихся футеров.
- Сохранить иерархию заголовков и, для кода, границы функций и классов.
- Нормализовать Unicode (NFC), пробелы и переводы строк. Имена, коды, даты и проверочные числа не переписывать и не склонять.
- Не разрывать факт и его формулировку. Проверочный факт оформлять одним законченным предложением или одной парой «поле: значение», чтобы граница чанка не разрезала число и название.
- Удалить точные дубли. Корпус от 500 КБ небольшой, но BM25 и RRF вернут почти одинаковые чанки, и оба получат «yes» от грейдера.
- В комплекте держать все три семейства форматов, даже если основная база — заметки: приёмка проверяет поддержку `.md`, `.txt`, кода, `.json` и `.yaml`.

## Чанкинг по типу файла

Один рекурсивный сплиттер по символам на все файлы заданию не соответствует: оно отдельно просит подход из природы данных.

### Текст (`.md`, `.txt`)

Резать по заголовкам, затем по абзацам и предложениям. Короткий подраздел — один чанк. Длинный — несколько, только по границам абзацев. Список не отрывать от вводной строки. В начало текста чанка вставлять документ и путь раздела, тем же текстом, который уйдёт в эмбеддинг:

```text
Документ: <имя файла>
Раздел: <H1 > H2 > H3>

<абзацы подраздела>
```

Символы `#` в эмбеддинг не передавать: для модели это шум, путь раздела уже есть обычными словами.

### Код (`.py`, `.js`, `.ts`)

Единица — функция, метод или класс, а не N символов. Пример из задания (`TOKEN_EXPIRY_HOURS` против вопроса «как работает авторизация») как раз про это: идентификатор и окружающий код должны лежать в одном чанке, иначе BM25 найдёт обрывок, а грейдер не поймёт, к чему он относится. В текст чанка добавлять путь файла и имя символа. Крупный класс делить по методам, повторяя имя класса в каждом куске.

### JSON и YAML

Единица — объект или логический ключ верхнего уровня, а не разрез посередине значения. В чанке повторять путь ключа (`auth.token.expiry_hours: 720`). Большой список однотипных записей собирать по 5–15 элементов с повторением имени поля. Пару «ключ: значение» не разрывать: по ней работает и BM25, и точечный вопрос.

## Размер

Считать токенизатором той модели эмбеддингов, которая включена в конфиге, а не символами.

| Режим | Цель | Потолок | Зачем |
|---|---|---|---|
| Обязательный, эмбеддинги Chroma | 120–220 токенов | ~256 токенов | Длиннее дефолтное окно обрежет хвост, и вектор строится не по всему чанку |
| Необязательный, `nomic-embed-text` | 250–500 токенов | ~800 токенов | Окно эмбеддинга длинное, но грейдер и генератор — модель на 3–4B |

Ниже ~80–100 токенов чанк обычно не содержит законченной мысли, и оценка «yes/no» становится случайной. Выше потолка страдают и эмбеддинг, и промпт генерации: в контекст попадает несколько чанков плюс два возможных повтора поиска.

Перекрытие между законченными разделами, функциями и JSON-объектами не нужно. Если длинный раздел пришлось разрезать, переносить 1–2 предложения. Большой фиксированный overlap даст почти копии, и RRF поднимет их все.

Отдельная схема parent-child в графе задания не описана. Поиск, оценка и генерация работают с одним и тем же чанком. Самодостаточный чанк с путём раздела закрывает эту схему без второго уровня.

## Метаданные

Минимум по критерию приёмки — источник и позиция. Для грейдера, цитаты в ответе и `find_relevant_docs` этого мало, но лишние поля не требуют отдельного инструмента.

```json
{
  "source": "sample_docs/auth.md",
  "position": "lines 40-68",
  "chunk_index": 3,
  "file_type": "md",
  "section_path": ["Авторизация", "Срок токена"],
  "symbol": null
}
```

Для кода в `symbol` писать имя функции или класса, для JSON/YAML — путь ключа. `source` и `section_path` дублировать в тексте чанка: эмбеддинг и BM25 метаданные не читают, их видит только фильтр и финальный ответ.

## Как это стыкуется с Corrective RAG

- Узкий первый запрос ищет точный термин. Он находится, только если идентификатор, имя или проверочное число не разрезаны.
- Смысловой запрос ищет раздел. Он находится, только если в чанке есть путь заголовка и законченные абзацы, а не обрывки по 200 символов.
- Грейдер видит чанк без соседей. Если контекст только в предыдущем куске, релевантный фрагмент получит «no», сработает расширение запроса, и двух циклов может не хватить.
- Генерация на модели 3–4B собирает ответ из нескольких прошедших оценку чанков. Дубликаты и простыни вытесняют единственный чанк с проверочным фактом.

## Что зафиксировать в отчёте

Задание требует описать выбранный подход, а не ограничиться фразой «использовали RecursiveCharacterTextSplitter». В отчёте достаточно четырёх пунктов:

- отдельные правила для текста, кода и JSON/YAML;
- целевой размер в токенах активной embedding-модели и почему он не выше её окна;
- overlap только на принудительном разрезе;
- метаданные `source` и позиция плюс путь раздела в тексте чанка.

Проверку стратегии делать на проверочных фактах из README: точный идентификатор должен находиться через `find_relevant_docs`, а `ask_question` должен вернуть факт и файл-источник, а не общий ответ модели.
