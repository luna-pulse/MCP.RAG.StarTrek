# База данных

## Выбрано: ChromaDB

Для этого RAG-корпуса выбрана ChromaDB. Это локальное векторное хранилище: оно работает внутри процесса MCP-сервера, отдельный сервер базы не нужен. В одной коллекции лежат текст чанка, метаданные и вектор. Исходные файлы из `SourceFiles` остаются на диске и в базу целиком не копируются.

Точный поиск по именам, номерам кораблей и кодам вроде `NCC-1701-D` делает не ChromaDB, а индекс BM25 в памяти (`rank_bm25`). Его пересобирает `index_folder`. Два списка — векторный и BM25 — сливаются через Reciprocal Rank Fusion (RRF). Так устроен гибридный поиск в задании.

Сравнивались четыре варианта: ChromaDB, PostgreSQL с pgvector, MySQL и ClickHouse.

## 1. Что хранилище должно уметь

Корпус небольшой: сотни файлов и несколько тысяч чанков. Нагрузка — индексация папки и точечный поиск по вопросу, а не аналитика по миллиардам событий.

Хранилищу нужны четыре вещи одновременно:

- запись на каждый чанк: текст, вектор и метаданные (источник, позиция, путь раздела);
- фильтр по метаданным, чтобы переиндексировать один файл и не трогать остальные;
- векторный поиск по смыслу вопроса;
- сохранение коллекции на диск, чтобы индекс пережил перезапуск сервера.

Связь «чанк принадлежит файлу» держит индексатор: стабильный идентификатор чанка и удаление старых записей этого файла перед новой записью. Хеш содержимого файла кладётся в метаданные, чтобы заметить правку и пересобрать только его чанки.

Полнотекстовый поиск по русскому в самой базе заданием не требуется. Точные обозначения ищет BM25.

## 2. Почему ChromaDB

ChromaDB закрывает схему из задания одной библиотекой.

- Задание прямо называет ChromaDB векторным хранилищем: in-process, без отдельного сервера. В Docker Compose остаются сервер и Ollama.
- LangChain отдаёт коллекцию в гибридный поиск (`EnsembleRetriever`: вектор + BM25, затем RRF).
- Текст чанка, эмбеддинг и метаданные лежат в одной записи коллекции. Ответ не собирается из двух баз.
- `PersistentClient` пишет коллекцию в папку на диске. Для курсового проекта этого достаточно.
- Эмбеддинги по умолчанию встроены в ChromaDB. Внешняя модель (`nomic-embed-text` через Ollama) подключается конфигом, без смены остального кода. Это необязательный пункт задания.
- Обновление файла — удалить записи с этим `source` и добавить чанки заново. `index_folder` после этого заново строит BM25.

Размер вектора задаёт выбранная модель. Встроенная модель ChromaDB (`all-MiniLM-L6-v2`) даёт 384 измерения. `nomic-embed-text` даёт 768. Смена модели означает новую коллекцию и полную переиндексацию: старые векторы с новой моделью не сравниваются.

## 3. ChromaDB

Плюсы:

- Нет отдельного сервера базы. Сервер MCP открывает коллекцию как библиотеку. Установка и запуск проще, чем у PostgreSQL.
- Текст, вектор и метаданные — одна запись. Поиск по смыслу и фильтр по файлу идут в один запрос.
- Есть фильтры по метаданным: источник, тип файла, тип сущности. Так отсекаются чужие чанки до ранжирования.
- Объём в несколько тысяч чанков для ChromaDB обычный. Отдельный кластер не нужен.
- Индекс HNSW и косинусное расстояние уже внутри. Свой индекс векторов писать не надо.
- Встроенные эмбеддинги позволяют поднять поиск без второй модели. Переключение на Ollama остаётся в конфиге.
- Локальная папка с данными нормально живёт рядом с проектом на Windows и в томе Docker.
- API короткое: создать коллекцию, добавить чанки, найти top-k, удалить по фильтру. Это совпадает с инструментами `index_folder`, `find_relevant_docs` и `index_status`.

Минусы:

- Нет внешних ключей и проверок `CHECK`. Пустой текст, чанк без файла или две записи с одним идентификатором ловит код индексатора, а не база.
- Точный поиск по русским именам и кодам в ChromaDB слабый. Его закрывает отдельный BM25 в памяти. Два индекса нужно держать согласованными: после каждой индексации BM25 строится заново из тех же чанков.
- Встроенная модель `all-MiniLM-L6-v2` заточена под английский и обрезает текст около 256 токенов. На русском корпусе смысловой поиск слабее, пока конфиг не переключён на модель вроде `nomic-embed-text`.
- Метаданные — скаляры: строка, число, логическое значение. Путь раздела и список заголовков хранятся строкой, не вложенным объектом.
- Смена размерности эмбеддинга не делается правкой столбца. Нужна новая коллекция и полный пересчёт векторов.
- Папка данных — часть состояния сервера. Без тома Docker индекс пропадёт при пересоздании контейнера.
- На миллионах векторов и при нескольких писателях сразу удобнее серверная база. Для этого корпуса такого объёма нет.
- Журнал вопросов, задержки и статистику ответов ChromaDB не ведёт. Это другая задача, и для неё она не подходит.

## 4. PostgreSQL с pgvector

Плюсы:

- Вектор, текст чанка и метаданные можно положить в одну строку. Индекс HNSW и косинусное расстояние есть в pgvector.
- Внешние ключи, уникальность и `CHECK` держат связь файла и чанка внутри базы.
- Полнотекстовый поиск по-русски (`tsvector`) сам находит имена и коды вроде `NCC-1701-D`.
- Точечное обновление одной строки привычное: поправили файл, пересчитали вектор, записали обратно.
- На нескольких тысячах строк запас по объёму большой.

Минусы:

- Задание фиксирует ChromaDB и BM25 через `rank_bm25`. Свой полнотекстовый поиск PostgreSQL дублировал бы уже заданную схему.
- Это отдельный сервер: установка, пользователь, порт, сервис в Docker Compose. Для in-process MCP это лишний процесс.
- Размер вектора задаётся при создании столбца. Другая модель — другой столбец и переиндексация.
- Индекс HNSW занимает память и строится заново после массовой загрузки.
- Встроенных эмбеддингов нет. Модель нужна сразу, а в задании модель по умолчанию — та, что идёт с ChromaDB.

## 5. MySQL

Плюсы:

- Хорошо хранит текст, карточки файлов и связи между файлом и чанками.
- Внешние ключи и ограничения есть и работают привычно.
- Широко встречается в учебных курсах, много готовых инструкций по установке.
- В MySQL 9 есть тип `VECTOR`: вектор можно положить в ту же базу, что и текст.

Минусы:

- Векторный поиск моложе экосистемы pgvector и ChromaDB: меньше примеров RAG на LangChain, слабее связка с фильтрами по метаданным.
- Полнотекстовый поиск по русскому слабее, чем `tsvector` в PostgreSQL. Имена и коды вроде `NCC-1701-D` как раз тот случай, где это заметно.
- Практичная схема часто распадается на две части: MySQL для текста и отдельное векторное хранилище. Две системы сложнее держать согласованными.
- Отдельный сервер MySQL задание не предусматривает. Для этого корпуса выигрыша нет: объём маленький, а гибридный поиск уже задан парой ChromaDB + BM25.

## 6. ClickHouse

Плюсы:

- Быстро считает агрегаты по большим журналам: события, просмотры, логи запросов.
- Колоночное хранение хорошо сжимает однотипные числовые поля.
- Умеет приближённый поиск по векторам на больших объёмах, если записей уже миллионы и больше.
- Удобен, если позже понадобится отдельно разбирать журнал вопросов к RAG.

Минусы:

- Это аналитическая база. Строки здесь чаще дописывают пачками, чем правят по одной при переиндексации файла.
- Внешние ключи не держат связь «чанк принадлежит файлу». Целостность всё равно пришлось бы проверять в коде загрузки.
- Частые точечные обновления эмбеддинга тяжёлые: правка строки превращается в перезапись куска данных.
- На нескольких тысячах чанков скорость ClickHouse не даёт преимущества. Накладные расходы на движок больше пользы.
- Полнотекстовый поиск по русским статьям — не его основная задача.
- Рядом с MCP-сервером это ещё один сервер, которого нет в схеме задания.

ClickHouse имеет смысл позже и отдельно: журнал вопросов, какие чанки вернулись и сколько занял ответ. Сам корпус в него класть не стоит.

Выбор: ChromaDB. Она совпадает с заданием, держит чанки и векторы в процессе MCP-сервера и стыкуется с BM25 для гибридного поиска. PostgreSQL с pgvector сильнее по ограничениям и русскому полнотекстовому поиску, но для этой работы это другой контур, чем указан в задании. MySQL умеет хранить те же карточки и хуже закрывает векторный поиск. ClickHouse оставляют для аналитики по журналу запросов, если она понадобится отдельно.
