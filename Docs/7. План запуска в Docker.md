# План запуска индексатора в Docker

Консоль `StarTrek.Indexer` должна собираться и запускаться в Docker. Проверка этого плана — только команда `health-check`. Команды `analyze`, `chunk` и `embed` в проверке не запускаются, корпус в ChromaDB не пишется, папки `Data/`, `ChromaDB/` и `SourceFiles/` не меняются.

## Что меняется

- `src/StarTrek.Indexer/Commands/CommandDispatcher.cs` — новая команда `health-check` и строка в справке.
- `Dockerfile` в корне репозитория — многостадийная сборка и публикация.
- `.dockerignore` в корне — чтобы контекст сборки не тащил лишнее.
- `docker-compose.yml` — сервис `indexer` рядом с уже существующим `chromadb`. Том Chroma остаётся `./ChromaDB:/data`: образ Chroma ждёт каталог `/data`.
- `README.md` — короткий раздел про образ индексатора и `health-check`.

`src/StarTrek.Indexer/appsettings.json` не меняется. Локальный адрес Chroma остаётся `http://127.0.0.1:8000`, чтобы `dotnet run` на машине разработчика работал как раньше. Внутри Compose адрес задаётся переменной окружения.

Тесты не добавляются и не правятся.

## Команда health-check

Имя команды — `health-check` (строчные буквы, через дефис), в том же стиле, что `analyze`, `chunk`, `embed`.

Поведение:

- печатает в stdout одну короткую строку: `Индексатор отвечает: healthy.`;
- возвращает код выхода 0;
- не принимает параметров.

Ветка `health-check` в `CommandDispatcher` не вызывает `GetRequiredService` для `AnalyzeCommand`, `ChunkCommand`, `EmbedCommand`, `E5Tokenizer` и генератора ONNX. Эти сервисы по-прежнему регистрируются лениво и создаются только когда их команда реально выполняется. Иначе старт потребует `tokenizer.json` и `model.onnx`.

Неизвестная команда по-прежнему пишет ошибку и возвращает код 2. Пустой список аргументов по-прежнему печатает справку и возвращает 2. Справка перечисляет `health-check`.

`health-check` не открывает корпус, не читает `model.onnx` и не делает запросов к ChromaDB. `ValidateOnStart` по-прежнему проверяет только строки настроек, а не наличие файлов корпуса.

Процесс по-прежнему ищет корень репозитория через `RepositoryPathResolver`: вверх от текущей папки и от `AppContext.BaseDirectory`, пока не найдётся `MCP.RAG.StarTrek.sln`. Рядом с программой должен находиться `appsettings.json` (его кладёт `dotnet publish`, потому что в csproj стоит `CopyToOutputDirectory`).

## Образ

Базовые образы — glibc, не Alpine: проект ссылается на `Microsoft.ML.OnnxRuntime`, даже если `health-check` модель не грузит.

- сборка: `mcr.microsoft.com/dotnet/sdk:10.0`
- запуск: `mcr.microsoft.com/dotnet/runtime:10.0`

В стадии сборки копируются `global.json` (пин SDK `10.0.401`, `rollForward: latestPatch`), `MCP.RAG.StarTrek.sln` и каталог `src/StarTrek.Indexer`. Публикация: `dotnet publish` проекта индексатора в конфигурации Release. Тестовый проект в образ не входит.

В финальном образе раскладка такая:

```text
/opt/startrek/MCP.RAG.StarTrek.sln
/opt/startrek/app/StarTrek.Indexer.dll
/opt/startrek/app/appsettings.json
```

Рабочая папка — `/opt/startrek/app`. Файл решения лежит на уровень выше, поэтому `FindRepositoryRoot` его находит. `model.onnx` в образ не копируется.

`ENTRYPOINT` — `dotnet StarTrek.Indexer.dll`. `CMD` — `health-check`. Аргумент `docker compose run … health-check` подменяет только `CMD` и не затирает запуск `dotnet`.

## Compose

Сервис `indexer`:

- образ `startrek-indexer`, контейнер `startrek-indexer`;
- собирается из `Dockerfile` в корне;
- `depends_on: chromadb` — только порядок запуска, без обращения к API Chroma из `health-check`;
- переменная `STARTREK_Indexer__Chroma__Endpoint=http://chromadb:8000` (префикс `STARTREK_`, разделитель `__`);
- команда по умолчанию — `health-check`, поэтому `docker compose up` и `docker compose run` не индексируют корпус;
- политики `restart` у индексатора нет: команда завершается и не должна крутиться заново.

Сервис `chromadb` не переименовывается: образ `chromadb/chroma:1.5.9`, контейнер `startrek-chromadb`, порты `8000:8000`, том `./ChromaDB:/data`.

## .dockerignore

Из контекста сборки исключаются:

- `**/bin/` и `**/obj/`;
- `.git`;
- `Tests/` (тесты для образа не нужны);
- `Models/multilingual-e5-small/model.onnx`;
- `Data/`, `ChromaDB/`, `SourceFiles/` — для компиляции и для `health-check` не нужны, в контекст их не кладём.

Это исключение из контекста сборки, а не удаление файлов на диске.

## Как проверить, ничего не индексируя

Собрать образ и запустить только `health-check`:

```powershell
docker compose build indexer
docker compose run --rm -T --no-deps indexer health-check
```

`--no-deps` не поднимает ChromaDB. Если порт 8000 уже занят существующим контейнером Chroma, данные не трогаем: не выполняем `docker compose down -v` и не очищаем `./ChromaDB`.

Ожидание: код выхода 0 и строка `Индексатор отвечает: healthy.` в stdout.

Не запускать `analyze`, `chunk`, `embed` — ни локально, ни в контейнере. Не вызывать поиск.
